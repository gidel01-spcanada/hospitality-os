# Database foundation

## Overview

The database foundation for Afrik Appart is intentionally normalized and aligned with the requirements in the master prompt. Tables are designed for MySQL 8.x with utf8mb4, foreign keys, indexes, and a clean migration path.

## Core domain tables

- `establishments`: owning property groups and legal entity information.
- `properties`: each rentable unit with metadata, occupancy, pricing, and state.
- `amenities` and `property_amenities`: storefront amenity metadata and join records.
- `property_images`: files for each property, including cover image and ordering.
- `rate_rules`: nightly override pricing and minimum-stay logic.
- `reservation_guests`: guest snapshot information for declarations/privacy minimization.
- `reservations`: booking lifecycle record with check-in, check-out, pricing, and status.
- `payment_attempts`: payment provider references and normalized status history.
- `reservation_price_lines`: price breakdowns for the reservation total.
- `currency_configs`: configuration for conversion and supported currencies.
- `admin_availability_blocks`: staff-maintained dates unavailable for booking.
- `external_calendar_feeds` and `external_calendar_events`: iCalendar import and feed synchronization records.
- `cleaning_visits`: scheduled housekeeping/concierge visits linked to properties and optionally reservations.
- `cleaning_schedule_shares`: revocable, expiring, property-scoped public week/month schedule links.
- `settings`: app configuration values for locale, pricing, and internal toggles.
- `email_outbox`: transactional email queue and status monitoring.
- `audit_logs`: staff action tracking and operational review.

## Money and dates

- Monetary fields use `DECIMAL(12,2)` for amounts and `DECIMAL(12,6)` for exchange-rate configuration.
- Currency codes are stored as uppercase ISO codes such as `XOF` and `EUR`.
- Booking dates are stored as `DATE` values for date-range logic and calendar checks.

## Indexing strategy

The schema includes indexes for the fields required by the project brief, including property/date availability checks, reservation references, slug lookups, and calendar freshness checks.

## Schema installation

Two installation modes are provided:

1. MySQL clean install via `database/schema.sql` for phpMyAdmin or direct import.
2. Laravel migration-based install via the files in `database/migrations`.

For local validation, the project uses SQLite by default via Laravel, while the SQL schema remains MySQL-compatible and deployable to BlueHost.

## Seed data

- `database/seed.sql` contains reference data such as amenities, app settings, and currency parity.
- `database/sample-data.sql` contains the draft initial establishment and four apartment entries based on the supplied source set.

## Notes

- The initial property records are intentionally marked as draft content pending owner confirmation.
- The project stores only relative file paths for media, not database blobs.
- All key values and provider settings remain environment-driven and must not be committed to source control.

## Public Establishment Pages

- Apply Laravel migrations with `php artisan migrate --force` after deployment. The establishment publication migration adds `is_published`, defaulting to true for existing records.
- A public establishment must have both `is_active` and `is_published` enabled. The admin establishment editor has a publication checkbox. Its homes are public only when the property is active and its status is `published`.
- Public establishments appear in `/establishments` and `/sitemap.xml`, including those with no published homes. Empty or fully filtered-out establishments display a localized empty state.
- The sitemap is generated by Laravel, not a fixed public XML file. Deploy the updated public `.htaccess` as well as the application; its sitemap rewrite also overrides stale physical sitemap files left on an existing Apache deployment. The SEO deployment helper uploads the rewrite configuration rather than a sitemap snapshot.
- The detail-page gallery starts with `establishments.cover_image`, then one explicit primary photo per active, published associated home (the `is_cover` image record, otherwise `properties.cover_image`). Non-primary images and homes from other establishments are excluded; missing primary photos are skipped and URLs deduplicated. Existing extra establishment images from `metadata.gallery_images` follow the home covers. Search filters do not alter this gallery.
- The establishment directory and checkout establishment block still use only explicit establishment photos from `cover_image` / `metadata.gallery_images`. Each property card and checkout property block uses that property's own cover/image records. The amenity list comes from active, published homes; services use the active-locale establishment translation and active property features.
- The review section consolidates active direct establishment reviews (`establishment_id` matches, `property_id` is null) and active reviews whose property belongs to the establishment, including former/unpublished homes. A non-null property reference is scoped by property ownership, not solely by an establishment ID on the review. One SQL predicate returns each review ID once; the global rating is the average of individual ratings, not an average of property averages.
- Reviews are paginated newest-first with a stable ID tie-breaker. Origin/home filters affect only the review list; the global count/rating and structured data stay consolidated. Property attribution is localized; unpublished homes are named without a public link. Search filters do not alter the establishment rating, gallery, or service list.
- Nearby places are optional owner-provided metadata, not inferred distances or landmarks. Store localized entries under `establishments.metadata.nearby_points_of_interest`:

```json
{
	"nearby_points_of_interest": {
		"fr": [{ "name": "Marche local", "description": "Produits frais" }],
		"en": [{ "name": "Local market", "description": "Fresh produce" }]
	}
}
```

- The public page renders only the current locale's nearby entries. Omit the metadata when no verified information is available. Contact details and structured data omit invalid or draft placeholder values.
- The checkout order summary displays saved `reservation_price_lines`, not current catalog rates. Its night/unit breakdown is derived from the saved accommodation line, and its payable total is always `reservations.total_amount`. When legacy records have no price lines, the summary displays saved subtotal/fees/taxes and any remaining total adjustment without inventing a promotion or recalculating a payment.
- `App\Support\ReservationSummary` projects the same saved invoice, stay/media data and verified payment balance for checkout and reservation emails. Only `paid`/`completed` attempts count, guarantees are excluded, and repeated provider references are counted once. Pending proofs/authorizations are not paid amounts. Foreign-currency payments without a stored reconciliation are shown in their own currency rather than converted using a current/assumed rate; an uncertain balance is explicitly marked for reconciliation.
- Reservation-created/received/status emails share an email-compatible summary partial and layout. The outbox stores a summary plus reservation ID and refreshes reservation/payment facts at dispatch for the same recipient, avoiding stale balances after a delayed send. Existing checkout/review links and legacy outbox payload rendering remain supported.

## Deferred Account Activation

- The reservation migration `2026_10_03_000001_add_account_setup_deferred_to_reservations` adds `account_setup_deferred`, defaulting to false for existing reservations. Apply migrations on deployment with `php artisan migrate --force`.
- When a public reservation uses an existing unconfirmed customer email, reuse that user and save the reservation with `account_setup_deferred = true`. Do not log the guest in, change the account's activation/active status, or create a second user.
- Such reservations display the full checkout with a nonblocking activation notice and the existing password-setup email action. Payment still requires the normal checkout token and follows the unchanged payment verification workflow.
- Account-setup mail is sent after the reservation exists, with a return link to its checkout. Delivery failures are logged and reported without discarding the reservation or preventing payment. Reopening the checkout does not itself resend an email.
- Password setup through the emailed reset token confirms the email, leaves the saved reservation associated with the same user, and lets the customer log in to see it after payment. A matching old pending-reservation session entry is cleared to prevent duplicate booking on later login.
- Existing verified customers still follow login/reservation handling. First-time emails still follow the existing account creation and confirmation flow. Older checkout identity screens and their skip option are unchanged for reservations without the deferred flag.
