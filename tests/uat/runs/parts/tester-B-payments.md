## Defects

- D1 (P0, blocker): `POST /webhooks/{provider}` returns HTTP 419 "Session expirée" for every call that has no session cookie and CSRF token, including correctly signed ones. No CSRF exclusion exists in bootstrap/app.php, app/Http/Middleware or app/Providers. Provider callbacks can never confirm or fail a payment on a deployed stack. Cases: INT-001..010, INT-014, INT-019, PAY-023, PAY-024, PAY-027, PAY-028. Repro: `curl -X POST http://127.0.0.1:8102/webhooks/fedapay -H "X-Webhook-Signature: <valid hmac>" -d '{"reference":"x","status":"paid"}'` returns 419. With a session cookie and `X-CSRF-TOKEN` the handler works as specified.
- D2 (environment, blocks cases): receipt PDF download returns HTTP 500 because `Barryvdh\DomPDF\Facade\Pdf` is not found. composer.json requires `barryvdh/laravel-dompdf ^3.1` but `vendor/barryvdh` is missing in this checkout. Cases: PAY-035, PAY-036, INT-039 (also INT-004 step 5, INT-038 step 4). Repro: owner opens `/reservations/{id}/receipt` for a confirmed reservation. Fix on tester side: `composer install`.
- D3 (high if PayPal sandbox mode is left on in production): PayPal capture in sandbox mode confirms the reservation for any `orderID`, including no previous order, with no payment. Case PAY-021. Repro: POST `/reservations/{id}/checkout/paypal/capture?token=<token>` with `orderID=UAT-NOT-CAPTURED`; returns `COMPLETED`, reservation confirmed, receipt queued.
- D3b (medium): PayPal order for an XOF reservation with no establishment secondary currency is created as 100 000 EUR (amount not converted). Case PAY-020 step 5. Repro: POST `.../paypal/create` on a 100 000 XOF reservation with no secondary currency.
- D4 (medium): the checkout page renders only the `status` flash. `error` flashes ("Payment is awaiting confirmation.", "Payment is still awaiting verification.") are redirected with but never displayed to the guest. Cases: PAY-023, PAY-024, PAY-016. Repro: open `/reservations/{id}/checkout/fedapay/return?token=<token>` before payment.
- D5 (medium): provider `cancel_url` points at the POST-only `checkout.cancel` route; a GET returns a 404 page with only a link to the home page. Case PAY-022.
- D6 (high, double booking): a signed paid webhook for a reservation that was cancelled, after another guest confirmed the same property and dates, sets the cancelled reservation back to confirmed with no alert or manual-review status. Case INT-019 (needs D1 workaround to reproduce).
- D7 (low): each replayed paid webhook queues another `reservation_status_updated` email; `receipts` has no unique index on `payment_attempt_id` (concurrent replays still produced one receipt in the test). Cases: INT-005, INT-006, PAY-028.
- D8 (product decisions): webhook amount and currency are not compared with the stored attempt (INT-015); a webhook for provider X can pay an attempt of provider Y in sandbox gateways (INT-018).
- D9 (medium, privacy): stored payment proofs under `public/uploads/reservations/<id>/` are downloadable anonymously by direct URL (HTTP 200) when the file name is known. Cases: PAY-031, INT-040.
- D10 (low): the HTML error pages for 410 and 422 aborts show no specific message (410 uses the default Symfony "Gone" page; 422 shows a generic "Données invalides" page); the message appears only in JSON. Cases: PAY-007, PAY-008.
- D11 (low, documented): a signed sandbox webhook without a `status` key is treated as paid (INT-009 step 3). Also observed: repeated pay-on-arrival submissions create attempts with identical `idempotency_key` (PAY-015); an expired pending reservation keeps blocking its dates (PAY-008).

## Environment notes

- APP_ENV is `local` on instance 2 and cannot be changed by the tester, so non-local behaviour of `checkout.complete` (PAY-016, INT-016) was not observable.
- The instance php.ini sets `upload_max_filesize=2M`, so uploads above 2 MB fail before the application's 5120 KB rule (PAY-032 steps 2-3).
- The external exchange-rate API used for the Interac CAD conversion is unreachable, so Interac is hidden by default. For PAY-030 only, the cache key `exchange-rate:EUR:CAD` was seeded with 1.5 in the instance cache (simulated rate).
- Broken-SMTP checks (INT-037, INT-038) used a process-local env override (`MAIL_MAILER=smtp`, `127.0.0.1:1`) on the artisan command only; no external mail system was contacted. All other mail went to `storage/logs/laravel.log`.
- Setup changes on instance 2 DB: establishment 1 payment methods, secondary currency and cancellation fee settings were changed during the run and reset to null/0 at the end; synthetic `site_reviews` rows were removed; outbox rows from earlier steps were marked `sent` once to isolate counts in INT-037/038. Users created: b-cust1, b-cust2, b-host-other, guest-pay (all @example.test).
- Test uploads left in `public/uploads/reservations/` (untracked): reservation ids 132, 134, 135, 136, 143, 147, 152, 156, 158, 173 (one synthetic PDF/PNG each, plus any staff proof). Files under `public/uploads/reservations/1/` pre-existed and are not from this run.
- Case-text vs implementation notes: staff (admin) cannot open `/reservations/{id}/checkout` without the token (they are not owners and are redirected to the access page); the token link is needed for the staff steps in PAY-016.
